Section 00 · Orientation

How to read this, and what you should be able to do at the end

About forty minutes of reading, and a promise about what it buys you.

Read this straight through in order. Each section assumes the one before it and nothing after it, so skipping forward mostly produces confusion rather than speed. Sections 01 to 05 are the shape of the thing and are not optional; 06 to 09 are the machinery; 10 and 11 are what to do on your first day and what is honestly still missing.

The guide is written against the running system. Every version string, port number, byte budget and test count in it was taken from the code or from a live request on 2026-08-08, and where a number is the kind that goes stale, the reading is dated in place. When you read this months from now, treat the dated numbers as a snapshot and re-check them — the section on working on the service tells you the commands.

When you reach the end you should be able to answer these four questions without looking anything up. They are the questions this service is built around, and every one of them has a section that answers it.

Why can a record's identity be recomputed from its own contents?

Because identity is a hash of two things the record itself carries. Section 04.

Why is delivering the same chunk twice safe?

Because the same chunk under the same processing produces byte-identical output at a stable address. Sections 04 and 08.

What happens when one model server dies mid-chunk?

It depends entirely on whether the stage that was calling it was required or optional. Sections 06 and 07.

How can you tell "nothing was there" from "we failed" from "we never tried"?

From the record together with the string naming the processing that produced it — the dialect, defined in section 02. The distinction is the point of the whole design. Section 06.

Section 01 · The job

What the service is for, and the two boundaries it lives between

One job, two contracts, and a quality ceiling for the entire product.

Nucleus is building a model of one person, trained night after night on that person's own captured life. Something has to stand between the raw capture — an audio blob, a screen recording — and a trainer that can only learn from language. That is this service. We turn bytes into sentences with timestamps on them.

The consequence is worth sitting with before you read any code. Every token the personal model is ever trained on passed through this pipeline. If we transcribe a sentence wrongly, the model learns it wrongly, and nothing downstream can detect that it happened. There is no reviewer between us and the training set. That is why so much of what follows is about being able to tell, later and from the data alone, exactly what we did and did not do.

recording :8084— C1 → data-processing :8085— C2 → storage /context :8083→ continuum · nightly training

C1 comes in: an envelope, and bytes somewhere else

Recording carves a captured stream into chunks of a few seconds each. For every chunk it does two separate things: it writes the raw bytes to storage's /raw store first, and then it pushes us a small JSON envelope describing them. That envelope is contract C1. It carries who the user is, which device and which stream, a sequence number, the chunk's own id, the modality and codec, the wall-clock span, and a blob_ref pointing at the bytes recording already stored. We pull the bytes by that reference. That sequence number is dense: the first chunk of a stream is numbered zero and each later one adds exactly one, so a number that never arrives means a chunk was lost rather than never sent.

Two properties of this arrangement matter more than the rest. Delivery is at-least-once, which means recording may hand us the same chunk again — after a timeout, after a restart, after an operator asks it to — and it is our job to make that harmless rather than duplicative. And the device's own clock discipline rides along in the envelope: the timezone it believed it was in, its offset, and a flag saying whether its clock was synchronized. We copy all three onto the record verbatim and perform no timezone arithmetic of any kind (D17). A zone is a fact about where a person physically was, knowable only at the device and only at the moment of capture; anything we reconstructed later would be a guess wearing the costume of data.

C2 goes out: exactly one record

For each chunk we write exactly one processed record to storage's /context store. That record is contract C2, currently at version 1, and the next three sections are about almost nothing else. It carries provenance back to the chunk, the wall-clock span copied verbatim from the envelope, a string naming the processing that produced it, and a map of named slots holding what we actually found.

There is a third contract, and it is not builtThe charter also promises C8: the same pipeline offered synchronously to the input service, so that an interactive request — you paste a screenshot into a conversation — is normalized by the identical code that normalizes the life stream. No C8 surface exists today. What does exist is the inline ingest path described in section 08, kept deliberately as C8's skeleton; deleting it would orphan the contract before anybody builds it.

Everything else belongs to a neighbour. Recording owns capture and the devices. Storage owns /raw, /context and the day-log it renders for the trainer. Continuum owns the nightly fine-tune. We own the middle, and our obligation to all of them is the same: write down what was really there, and make it possible to tell afterwards what we did.

Section 02 · Language

Vocabulary — the twelve words the rest of this assumes

Each is defined here and used precisely everywhere after. None is decorative.

chunk

A few seconds of one captured stream, and the unit everything is keyed on. Recording carves streams into chunks; each has an id, and that id is how we recognise it again.

record

The one C2 object we write per chunk. Provenance, the time span, the dialect string, and a map of slots. Exactly one per chunk, and the machinery can only produce one.

slot

One named entry in a record's content.slots map — asr, diarization, transcript, acoustic, caption, ocr. Written by exactly one stage, exactly once, and never edited afterwards by anyone.

executor

The machinery that runs one chunk's stages: it works out which may start, runs them, collects each slot, and assembles the single record. When this guide says something holds "by construction", the executor is usually what constructs it.

stage

One processing step, declared in one file. It says what other stages it needs, which single slot it produces, whether it is required, and how many bytes its slot may occupy.

backend

The concrete implementation behind a stage — a model and the way it is called. Selected in code, never by configuration, and named in the version string so you can always see which one ran.

pipeline_version

Also called the dialect. A plain string naming every stage that was enabled and the versions it ran at, joined with plus signs in sorted order. It states what was attempted, and it is half of a record's identity.

segment

One stage's own piece of the dialect string, shaped <stage>.v<S>-<backend>.v<B>. Each slot carries a copy of its producer's segment, so a slot can name what made it without anyone re-parsing the whole dialect.

hole

A slot that was attempted and failed, and is therefore simply absent from the record. Distinct from a slot that is present and empty, which is a claim that we looked and found nothing.

heal

Re-running a chunk's whole graph on a later delivery to try to fill its holes, writing to the same record address. Bounded by a budget of three.

model server

A long-lived process that holds one model in memory and answers requests over HTTP. Four such models run under this service's own supervisor, two replicas each, and no model is ever loaded inside this service itself.

day-log

The rendered account of a span of someone's life that storage builds from our records, and the thing the trainer actually reads. Ours to feed, storage's to render.

Section 03 · The core

One chunk, one record, built from slots

If you keep one shape from this guide, keep this one. Everything else is machinery that protects it.

A chunk of captured life becomes exactly one record — precisely, one record per chunk per dialect, which is the qualifier that makes reprocessing under a new version safe rather than destructive, as the next two sections show. That record's content is not prose and not a fixed set of fields — it is a map of named slots, where each slot was written by exactly one stage, written once, and never touched again by anything else. Adding a second record for the same chunk is not a thing anyone can do by writing code carelessly; it would require changing the contract itself.

The pipeline that produced it is entirely real; the life inside it is not, because no captured day has yet flowed through this system (section 11) — this chunk comes from a synthetic soak feed reading a novel aloud, which is why its device is called mac-a. Why a map of slots, and not fieldsA fixed set of fields would mean that adding a capability — acoustic tagging, on-screen text — reshapes the contract for everybody, and that two steps writing near each other eventually write over each other. A map removes both problems at once. A new capability adds a key; nothing existing changes shape. And because each key has exactly one writer, "who wrote this" is answerable from the record alone, forever. The rule that makes it hold is that no stage may edit another stage's slot. When you want a view that combines two slots — a transcript with speakers attached to it — you do not edit either one. You add a stage that reads both and produces a third slot, which is exactly what transcript is in the record above.

Look again at the acoustic slot in the audio record. Its value is an empty list. That is not a bug and not missing data: it is the acoustic stage saying, on the record, that it ran and found no events worth naming. A slot that is present and empty is a claim. A slot that is absent is a different thing entirely, and section 06 is where that distinction gets its full weight.

Section 04 · Identity

Why a record's address can be recomputed from the record itself

Two components, one hash, and the reason at-least-once delivery stops being frightening.

A record's record_id is the SHA-256 of exactly two things joined by a zero byte: the chunk id, and the dialect string.

record_id = sha256( chunk_id + NUL + pipeline_version )

Both inputs are printed inside the record — source.chunk_id and pipeline_version — so anyone holding a record can recompute its address and check it. Here is that computation on the very record shown above, with its actual values — and the digest it produces is the record_id printed at the top of that record, which you can check for yourself:

Verified 2026-08-08 against both the record storage served and the service journal row for that chunk, which stores the same id.

Why a zero byte in the middle? Because without a separator that cannot appear in either component, two different pairs could concatenate into the same string and collide. Chunk ids and dialect strings are both text; a NUL byte is not text, so nothing can smuggle one across the boundary.

What determinism buys: exactly-once effects on an at-least-once wire

Now put the pieces together, because this is the single most useful idea in the service. Writing to storage is a blind upsert on record_id — storage does not ask whether it has seen the record, it simply writes it at that address. And the same chunk processed under the same dialect produces byte-identical output, because nothing time-varying is allowed inside a record. There is deliberately no "processed at" timestamp: a wall-clock field would make every reprocess differ, and the determinism test would go red.

So: deliver a chunk twice and the second pass computes the same address and writes the same bytes to it. The wire is at-least-once; the effect is exactly-once. Nobody has to coordinate, no locks are held across services, and a redelivery — from a retry, a restart, or an operator re-pushing a day — is simply harmless. Most of the durability machinery in section 08 exists to exploit this property rather than to work around its absence.

The corollary you will use constantlyChange the dialect and you change the address. A record processed under a new version does not overwrite the old one — it lands beside it, at a different id, and both exist in storage. That is what "version-forward" means everywhere in this service, and it is why bumping a version is a safe act rather than a destructive one.

Section 05 · The version law

The dialect: what ran, stated before anything runs

How the string is built, why no environment variable may ever change a record, and a live example of code and fleet disagreeing.

Every stage declares two version numbers. The stage version covers its contract — what it needs, what its slot is called and what shape that slot has, what it means to emit it, and its byte budget. The backend version covers its implementation — the model, the weights, the prompts, the thresholds, any behaviour at all. Together with their names they form the stage's segment:

<stage>.v<S>-<backend>.v<B>          asr.v1-fw.v1
                                     diarize.v1-pyannote.v1

The dialect for a run is every enabled stage's segment, sorted, joined with plus signs. It is composed during graph resolution — cheap string work over a handful of stages — before any stage executes. That ordering is not an implementation detail: it is what lets the string mean "attempted". A dialect naming four stages tells you four stages were tried. It never tells you four stages succeeded.

No environment variable may change what a record says

This is the part that surprises people who have worked on services where a knob tunes the output. Here, behaviour lives in code or it does not exist. A stage is never even handed the settings object: the context it receives carries the envelope, the raw bytes, its inputs and its clients, and no configuration at all. Environment variables do exist — twenty of them are declared — but every one is operational rather than output-affecting: where storage lives, which endpoint to call, how many workers to run, how long to wait, whether metrics are on.

This is enforced rather than encouraged. A determinism test runs the same fixed bytes through the pipeline across a matrix of environments and asserts the produced record is byte-identical every time, and a second check reads every environment variable the code touches and fails if a new name appears that has not been declared operational. If you find yourself reaching for a configuration value to change what a record contains, you are writing a code change, and it needs a version bump.

Which number do I bump?Change what the stage promises — its dependencies, its slot's name or shape, what emitting it means, its byte budget — and that is the stage version. Change how it keeps that promise — a different model, new weights, a reworded prompt, a moved threshold — and that is the backend version. If you are running an experiment, it must surface in the string as a .exp- suffix; an A/B that is invisible to identity is forbidden outright, because it would mean two records claiming to be the same thing while containing different answers.

Section 06 · The graph

Stages, readiness, and the three answers a record can give

How work is scheduled, what happens when a step fails, and the distinction the whole design exists to protect.

A stage is one file. It declares what it needs, what single slot it produces, whether it is required, how many bytes its slot may occupy, and who consumes it. Then it defines exactly one method: a synchronous one, which the executor runs in a worker thread so blocking work can never freeze the event loop, or an asynchronous one for stages that only make network calls. Inside this service, adding a processing step is adding one file: there is no registry to edit and no wiring to update. If the new stage emits a slot the record has never carried before, one thing does happen outside the file — the slot's name and shape are added to the C2 contract, because unknown slot names fail closed by design. Section 10 walks that through.

One thing to expect before you open the directory: the audio folder holds six stage files and only four of them appear here. Speech translation and an injected-caption stage used for replay work are both fully written and tested, and both are deliberately left unregistered — so they are absent from the dialect and never run.

The consumer column is a declaration every stage is required to make, and its prefix is part of the grammar: daylog: names a line the day-log renderer builds from the slot, stage: names another stage that consumes it during the run, and speculative: is an explicit admission that nothing reads it yet. A stage that cannot fill this in does not register at all.

Three further details in that table repay a second look. Needs names stages, not slots — speaker_align needs diarize, even though the slot it reads is called diarization. Naming the slot there is the most common first mistake and fails immediately with "needs unknown stage". A stage need not produce a slot at all: clipprep decodes video into frames that live only for the duration of the run and are freed the moment the last consumer finishes, so no bytes ever reach the record. And the byte budget is a hard ceiling, not a target: exceeding it is a stage failure, never a silent truncation, because a quietly shortened transcript is a lie that nothing downstream can detect. The budget of 1 on clipprep is not a typo and can never fire — every stage is required to declare a positive budget, and a stage that emits no slot gives the check nothing to measure.

A stage starts the moment the stages it needs have finished

There is no ordering attribute and no topological loop. Every stage becomes one task, all inside a single task group, and each task awaits exactly the futures of the stages it declared and nothing else. A stage with no dependencies starts immediately; a stage with dependencies starts the instant they finish. The graph therefore runs itself, and a slow step only ever delays the steps that genuinely need it.

The record that ships

Required and optional differ by construction, not by convention

When a required stage fails, there is no record. The task group cancels and awaits every sibling, the original exception is dug back out and re-raised, and the chunk attempt fails — which hands it to the worker's retry and dead-letter path, described in section 08. Nothing partial is ever written. When an optional stage fails, its slot is simply never written, every stage downstream of it is marked cancelled without running, and the record ships anyway carrying whatever else succeeded.

Because those two behaviours are so different, the resolver refuses outright to build a graph in which a required stage sits anywhere downstream of an optional one. If it allowed that, the optional stage's failure would cancel a required stage, which would mean no record — making the "optional" stage required in fact while claiming otherwise. Resolution happens the first time a modality is actually used rather than at boot, so a graph malformed in this way surfaces on the first chunk of that modality, not when the process starts.

The three states, and why they must stay distinguishable

This is the idea the entire service is arranged around. Given a record and its dialect, a consumer can distinguish three completely different situations — and if they ever collapsed into a single notion of "missing data", the model would be trained on inferences nobody is entitled to make.

We looked, there was nothing

Stage named in the dialect, slot present, value empty. "acoustic": {"values": []} — the tagger ran and heard nothing worth naming. A positive claim about silence.

We tried and failed

Stage named in the dialect, slot absent. A hole. Something went wrong — a model server was down, a budget was blown — and we are saying so rather than pretending.

We never tried

Stage not named in the dialect at all. This chunk was processed by a pipeline that did not include that step, so the record is silent about it and no conclusion may be drawn.

The rule that falls out of this is short and absolute: a consumer may never infer a negative from an absent slot under a dialect that did not attempt it. If the on-screen-text stage is not in the dialect, the correct reading is not "there was no text on the screen" — it is "nobody looked". Get this wrong downstream and the trainer learns that a person's screen was blank during hours it was never examined.

Section 07 · The fleet

Machinery and bureaucracy: where the models actually live

Four supervised models in eight processes, a fifth reached over the network, one supervisor that lives inside this service — and the shutdown behaviour you must get right.

The split at the centre of the design is between machinery and bureaucracy. Models are machinery: heavy, slow to load, and worth keeping warm. This service is bureaucracy: a thin asynchronous orchestrator that decides what to do, calls other people to do it, and writes down the result. No model is ever loaded inside this process. Every model runs as its own long-lived server process, holding its weights in memory, answering HTTP requests, and reporting what it is at /health. A stage is a client.

Four models run under this service's own supervisor, two replicas each, eight processes in total. Here is the live map, read from the manifest and confirmed against every replica on 2026-08-08. A server says what it is, and the client checks

Every server's /health returns an identity — the model name, the exact weight revisions, the framework versions, the device. The manifest records what each server is expected to be, and the client compares the two. A mismatch is not a warning to be logged and stepped over; the call fails with an identity error and a metric fires. This is what stops the most frightening class of silent corruption in a system like this: a replica quietly restarting onto different weights and producing subtly different transcripts under an unchanged dialect string, forever, with nothing in the data to reveal it.

What happens when a server dies mid-chunk

Two layers respond, and they respond to different things. The client handles the single call: it has a small budget of transient retries — three attempts in total by default — and it deals them round-robin across the server's replicas, which is the entire reason two of each exist. So one replica dying during a call is usually invisible: the second attempt lands on its twin and the chunk finishes normally. With two replicas the third attempt comes back round to the first, so the budget buys one genuine alternative and then one more try at each.

The supervisor handles the process. It polls each replica's health every five seconds, and after three consecutive failures it declares the replica down and restarts it, backing off along a ladder of one, two, five, ten and thirty seconds, resetting once a replica has been healthy for a minute. If the replica cannot be brought back before the retry budget is spent, the call fails — and then everything depends on the policy of the stage that made it. Diarization is optional, so its slot becomes a hole and the record still ships with a transcript. Speech recognition is required, so the chunk attempt fails and goes to the retry machinery instead.

The supervisor lives inside this process, and that has consequences

The supervisor is not a separate program. It is a task running inside the service's own event loop, started at startup when the deployment opts in, which makes this service the direct parent of all eight replicas. You can see it on the running node: when this was checked on 2026-08-08 the service was process 632026, and all eight model servers reported that process as their parent. The numbers change on every restart; the parentage does not.

How the fleet dies depends entirely on how this service dies, and the difference has bitten people:

A graceful stop takes the fleet with it

On a normal shutdown the service drains its queue, then walks the replicas and signals each one to terminate, waiting up to ten seconds before forcing it. The fleet goes down. Because replicas are reaped one at a time, a worst-case orderly shutdown takes a while — roughly the drain timeout plus ten seconds per replica.

A hard kill leaves all eight running

Kill the service with an unblockable signal and the shutdown code never executes, so nothing ever signals the replicas. All eight survive as orphans still holding their ports; six of them also still hold GPU memory, the two OCR replicas being CPU-only. A restarted service will fail to bind those ports until somebody reaps them by hand.

Get the reason right, because the obvious reason is wrongIt is tempting to explain the orphans by saying the replicas are started in their own sessions, so they do not die with their parent — and you will meet that explanation, compressed into a single clause, in the charter's own summary of this law. The observation about sessions is true, but it is not the cause. On Linux nothing kills a child when its parent dies — an orphan is simply re-parented and keeps running, session or no session. There is no parent-death signal configured anywhere in this codebase and no per-service control group to sweep. The actual reason the fleet survives is narrower and more useful to remember: an unblockable kill cannot be handled, so the shutdown path never runs, so nothing ever signals the replicas. The separate sessions exist for a different purpose entirely — they let the supervisor signal a replica's whole process tree without signalling itself.

Section 08 · Durability

The journal, the five verdicts, and healing

What survives a crash, how a redelivery is judged, and why a successful heal is never charged.

A chunk arrives at /ingest. The service can run it two ways, and both are real code paths. Inline means the whole pipeline runs inside the request and the reply carries the finished record's id. Async means the chunk is written down durably, acknowledged with a 202, and processed by a worker afterwards. Async is what the deployment runs; inline is kept deliberately as the skeleton of the synchronous contract that section 01 mentioned, and for a single chunk the two produce identical bytes.

Before any of that, the request passes a short sequence of gates in a fixed order — is this valid JSON, does it satisfy the C1 schema, do we have a pipeline registered for this modality — and each answers with its own status code: malformed JSON is a 400, an envelope that fails the C1 schema is a 422, and a modality we have no pipeline for is a 501. These are deterministic rejections, and they are answered synchronously in both modes, because a request that can never succeed should be told so immediately rather than accepted and then quietly dead-lettered later.

The claim tree: five verdicts on every delivery

Once a delivery is real work, the service asks the durable journal what it already knows about this chunk. That question has exactly five answers, and understanding them is understanding why redelivery is safe. The widget below offers six situations rather than five, because two quite different roads arrive at the same verdict of skip — one where everything succeeded the first time, and one where the budget for repair has run out.

Deliver a chunk · walk the claim tree

Healing, and the budget that bounds it

A heal is a full re-run of the chunk's graph, writing to the same record address — the dialect has not changed, so the identity has not changed either. The redelivery itself carries the original envelope, so nothing needed to be stored to make this possible.

Two rules govern the budget, and the second one is the subtle one. A heal that ends with holes still in it costs one attempt from a budget of three; when the budget is spent the holes are declared permanent, the row is marked final, and future deliveries of that chunk skip forever under that dialect. But a heal that comes back completely green is never charged. The budget exists to stop a chunk whose holes are structural from being re-run against the fleet forever; a heal that actually worked is not evidence of that pathology, so it does not consume the allowance.

A heal does not always make a record fullerIt is tempting to read healing as "the record only ever gets fuller". It does not. A heal re-posts whatever the re-run produced, so a heal that happens to run during a different server's outage can leave a record with a slot that was previously filled now missing. The guarantee is that repeated healing converges on a complete record, not that every individual step improves it. The hole truth lives in the journal's per-stage statuses, not in the record — which is why the journal, and not the record, is what you read when you want to know what has failed.

What survives a crash

The journal is a small SQLite database with two tables. A pending row is written before the 202 goes out, which is the whole reason the acknowledgement can be trusted: if the box dies a microsecond later, the row is still on disk and startup re-drives it. A processed row is the durable receipt, and it carries the per-stage statuses, the heal count, and the dialect the record was written under.

Killed at this momentWhat survivesWhat happens next
Before the pending row is writtenNothing on our sideRecording never got an acknowledgement, so it re-pushes. Processed as fresh.
After the pending row, before the 202The pending rowStartup finds it and re-drives it. Recording may also re-push; the two converge because the address is deterministic.
Mid-processing, after the 202The pending rowStartup re-drives the chunk and the whole graph runs again. Nothing partial was written to storage, because there is exactly one write per attempt.
After storage confirms, before the receipt is writtenThe record, in storageThe re-drive processes it again and writes byte-identical bytes to the same address. Harmless.
After the receipt is writtenEverythingA later delivery reads the receipt. If every stage was green it skips; if the receipt records holes and the repair budget is not spent, it heals instead.

When a required stage fails, the chunk does not go straight to a dead letter. The worker classifies the failure first. A transient one — a model server timing out, storage answering with a server error — is retried, a small number of times with a lengthening pause between attempts, and a chunk waiting out that pause gives up its slot so it cannot block the pool behind it. A terminal one — an envelope that produced an invalid record, a graph that cannot be resolved — is not retried at all, because trying the same thing again with the same code cannot possibly help. When the retries are exhausted, or immediately in the terminal case, the chunk is durably dead-lettered.

Two protections keep that table honest. Every acceptance bumps an epoch on the row, and terminal writes are guarded on it, so a worker that wakes up late and finishes a chunk a newer delivery has already re-accepted cannot clobber the fresh attempt. And the startup re-drive counts how many times it has automatically re-driven each chunk, so that a chunk which crashes the service on every attempt cannot crash-loop the box forever. Past the cap it takes one of two exits, and which one depends on whether a record already exists. A chunk that has never produced a record is dead-lettered. A chunk that already has a durable record — a repair attempt or a reprocess that keeps dying — is instead marked finished with its holes made permanent, because dead-lettering a chunk whose record is sitting in storage would report a loss that did not happen. A dead letter is durable and reported on /continuity, which is how recording learns that a chunk it handed us is genuinely lost rather than merely slow — so a lost chunk reads as a gap on its side, never as clean.

Section 09 · Downstream

Storage's side, and the line the trainer finally reads

Where the record lands, what makes it move between training windows, and how slots become sentences.

We make exactly one write per completed attempt: a single atomic POST of the whole record to storage's context store. Partial writes are forbidden — there is no state in which half a record exists.

Be careful about what the acknowledgement means, because the two ingest modes differ here and it is the difference that governs how you reason about crash windows. Inline, the reply is withheld until storage has confirmed the write, so a success reply really does mean the record is durable. Async — which is what the deployment runs — returns its 202 as soon as the chunk is safely journalled, long before any stage has run. That 202 promises only that we have durably taken responsibility for the chunk. What tells recording a chunk is genuinely done is not the acknowledgement at all: it is the chunk appearing as processed on /continuity, which happens only after storage has confirmed.

Storage keeps two timestamps that we never see and never set. created_at is the first time that record address was ever written. updated_at moves only when the newly posted record differs byte for byte from what is already stored. That comparison is the quiet hero of the whole redelivery story: a duplicate delivery re-posts identical bytes, the comparison finds no difference, and the record is not touched at all. It does not move to a new training window; it does not get re-learned. Meanwhile a heal that genuinely changed something does differ, so it does move — and flows into the next window to be trained on, which is a cost the design accepts deliberately.

Slots become lines

The day-log is storage's rendering of a span of life for the trainer, and it walks our slots by name. The routing is direct: the caption slot becomes a Scene line, the on-screen-text slot becomes a World text line, and the speaker-aligned transcript becomes speaker-bucketed Heard lines. If the aligned transcript is missing, the renderer falls back to the raw speech slot and renders it without speaker labels.

Which gives the honesty rules from section 06 their final consequence. A hole renders as absence — the line simply is not there. An empty value renders as nothing to say. Neither produces a sentence claiming the opposite, and neither is distinguishable from the other in the rendered text, which is exactly why the record and its dialect, not the day-log, are where you go to ask what actually happened.

Here is a real block from the live system, rendered from the same soak data as the record in section 03:

That window rendered 246 day-log segments — time slices of the window, an unrelated use of the word to the dialect segments of section 02 — into 23 blocks, in day-log format version 2 under recipe consolidation-v2.0.

Trace it backwards and you have the whole service. Those words were spoken into a microphone; recording carved them into a chunk and stored the bytes; we pulled the bytes, sent them to a speech model on port 8121, sent the same bytes to a diarization model on 8131, combined the two answers into a third slot, and wrote one record at an address derived from the chunk id and the dialect; storage compared it byte for byte with what it had, kept it, and rendered its transcript slot into that Heard line. Tonight the trainer reads the line.

Section 10 · Day one

Working on it

Adding a stage, running the suites, and the two traps that will cost you an afternoon.

Adding a stage is adding one file

Drop a file under the stage directory for your modality, subclass the stage base, decorate it so it registers itself, declare the surface, and write one run method. Discovery walks that directory and imports every module in it, so there is no registry to edit — though note that importing a file is not the same as enabling it. Only classes carrying the registration decorator enter the registry, which is how two of the six files in the audio directory sit there fully written and deliberately switched off. The declaration is checked hard at import: an invalid version number, a missing byte budget, a consumer that does not name who reads the slot, a dependency naming a stage nobody registered, or defining both run methods — each of these fails loudly at boot rather than mysteriously in production.

Then the checks the rest of the system will demand of you. Your slot name must be added to the C2 contract, because unknown slot names fail closed by design — that edit is the ceremony. Your byte budget must be a real number you can defend. Your consumer must be a real consumer today, or explicitly marked speculative. And if your stage changes what any existing record would contain, you have a version bump to make.

Running the suites

From the service root, with the service's own virtual environment:

cd product/services/data-processing
./.venv/bin/python -m pytest -q

On 2026-08-08 that run took 55.03 seconds and reported 569 passed, 4 skipped. The four skips are the drills that need real hardware — they spawn the model fleet on GPUs and only run when you ask for them explicitly.

Six test files carry the law itself, one per area: determinism against an environment matrix, one-record-per-chunk, dialect composition together with a snapshot of every stage's declared surface, the slot rules, the failure and ledger flows, and the honesty distinction from section 06. When you change the executor or a stage declaration, these are the ones that will tell you what you actually did.

Trap one: never run a hand-picked subset of the law testsRunning the determinism file and the composition file together produces two failures that do not exist in the full suite. The determinism tests import the stage modules for the first time under a deliberately emptied registry; Python caches modules, so the registration side effects can never fire again in that process, and the composition test then finds an empty registry and reports that the contract surface moved. The full suite stays green because other files import those stage modules earlier and normally, so by the time the determinism tests run, registration has already happened for real. A newcomer who "just runs the law files" gets a red on the exact test that guards the contract surface, and goes hunting in entirely the wrong place. Run the whole suite. If you must narrow it, know that the result is not trustworthy.

Trap two: nothing runs these for youThe charter describes the law as enforced in continuous integration. Today the only automated workflow in the repository checks the style of markdown files; no runner executes this suite. The discipline is yours, before you push. This is listed again in the next section, because it is the kind of gap that quietly becomes untrue in both directions.

Goldens and drills

Each model server keeps a golden: a recorded output of the real model on real bytes, with a written record of how its determinism was established. The stage tests replay that golden through a fake client and pin the resulting slot. The value of the two-hop arrangement is that a red test tells you which thing broke — the model stack, or your mapping of its output into a slot — because they live in different files. There is no regeneration script, deliberately: re-blessing a golden is a decision, and it rewrites the provenance note in the same commit.

The drills are the tests that need the real fleet, and they are worth reading even before you can run them, because they encode the operational discipline: the service is healthy before and after, no port is left listening, and GPU memory is checked as a delta rather than as an absolute.

Section 11 · Honesty

What is not built

Checked item by item against the tree and the running fleet on 2026-08-08. A guide that teaches the system we intend rather than the one we have misleads exactly the reader who cannot yet tell the difference.

GapWhere it actually stands
The captioner version bump has not reached the fleet Confirmed, not suspected. The code pins vlm.v2; the running service serves vlm.v1 and will until a deliberate restart. Section 05 explains the mechanism. Caption bytes are unchanged by the bump.
No full captured day has flowed end to end Real device captures have run: all three client surfaces were each driven on real hardware and verified. What has never happened is a complete captured day flowing through capture, processing, storage and training as one continuous piece. The streams visible on /continuity today have device names like phone-a and mac-a, but they are a synthetic soak feed built from fixtures — do not read them as real phones.
No real-GPU training run has consumed a current day-log One full training cycle has run over a current-format day-log, but with the mock trainer backend — the deterministic no-GPU path. Real-GPU training has certainly happened on this project; what has not happened is a real-GPU run consuming a day-log in the current format. The real trainer path is a scheduled cluster job.
The cross-service seam check cannot pass True, and precisely diagnosable: every record the script builds comes from one helper that stamps an older shape, and storage validates the current contract exclusively, so every write it attempts is rejected. Fixing the helper alone is not enough — the record id, the dialect string, where the modality sits and the whole content body all have to change. It is owed a rewrite; nothing blocks it.
One model server's dependencies are not fully pinned True. The acoustic server's requirements pin the framework but not the model-hub library, so rebuilding that environment from requirements alone does not reproduce what is running. Its two sibling servers do pin it. Worse than it first looks. The client's identity check compares only what the manifest pins — the model name and its weight revisions — so the framework versions a server reports are informational and are not compared at all. A drift in that library would therefore pass the identity check untouched.
The comparison apparatus for the older record shape is still retained True, and deliberately. It is a storage-owned executable check with 31 binding assertions, retained by a follow-up item on storage's board rather than by any capture milestone, and it can only be retired in one coordinated act rather than piecemeal, because more than one service leans on it.
No backfill-by-version tool exists True. Reprocessing semantics are fully built — the claim tree's version-forward branch works — but the operator tool that replays a day from kept raw bytes under a new dialect does not exist. Do not mistake one for the other.
/continuity reports dead letters but not holes True. The endpoint reports what was received, what is missing, what was processed and what was dead-lettered. Hole truth lives only in the journal's per-stage statuses, so a record that shipped with a failed optional stage is not visible on the wire.
Adapter hot-swap is designed, not built True at both ends. Storage resolves an adapter path and inference reads it and then never uses it; no adapter is ever loaded. Nothing in this service depends on it, but it is the reason the loop is not yet closed.
Nothing automatically runs the test suite Found while writing this guide. The charter and the board both describe the law as enforced in continuous integration; the only workflow in the repository checks markdown style. The law is executable and the tests are real — but a human has to run them.

Where to look next

Read the charter's Slot Law section in full — it is short, it is the law's only home, and every test file is written assuming you have read it. It is twelve numbered laws, and that matters practically: the code cites them by number constantly, so a comment reading "one enabled producer per slot (L5)" points at a specific paragraph of the charter rather than waving at a principle. Then the service board for what is open right now. Then the code, in this order: the stage base and the executor, which are the two files everything else orbits; then identity; then the journal. If you want one file that will hook you, read the honesty test — it implements a consumer reading a record from the record alone, and it is the clearest single expression of what this service is for.

If you remember five thingsOne chunk becomes one record. Its content is a map of slots, each written once by exactly one stage. Its address is a hash of the chunk id and the dialect, so redelivery is harmless. Behaviour lives in code, never in configuration, and a change to it moves a version number. And an absent slot, an empty slot and an unattempted stage are three different statements — keeping them distinguishable is the job.
