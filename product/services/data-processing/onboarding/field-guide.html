MODULE 00 Briefing

What you're joining, in sixty seconds

If you read nothing else today, read this card.

  • Nucleus is building a personal AI that fine-tunes a model on the user's own life, every night. Their life doesn't scroll out of a context window — it compounds into weights.
  • We are the translator in the middle. Recording hands us a few seconds of captured life; we write down what it contained — the words spoken, who spoke them, the scene on screen, the text in it — and hand that to storage.
  • Every token the model learns passes through us. There is no reviewer between our output and the training set. If we write it wrong, the model learns it wrong, and nothing downstream can tell.
  • One chunk becomes exactly one record. Its body is a map of named slots, and each slot is written by exactly one processing step and never edited by anyone.
  • A record's address is a hash of its own contents. That one trick makes delivering the same chunk twice completely harmless.
  • No model runs inside this service. Models are long-lived server processes we call over HTTP. We are a thin orchestrator that decides, calls, and writes down.
  • We are honest by construction. "We looked and found nothing", "we tried and failed", and "we never tried" stay three readable states, never one blurry idea of missing data.
How to read this guide

Modules 01–03 are the foundations: why we exist, the words, the shape of a record. 04–07 are the core machinery, and 07 is the heart — step a chunk through the service yourself. 08–10 go outward to the model fleet, crash safety, and what happens downstream. 11–12 are the judgment layer: why things are as they are, and what is honestly unbuilt. 13 gets you running code, and 14 is a quiz on traps that bite real sessions.

MODULE 01 The big picture

Why Nucleus exists, and where we sit

You can't reason about our design choices without the company's one big idea.

The one big idea: context becomes weights

Every AI assistant today meets its user fresh. Context windows grew, but a window is still a ceiling, and the model itself is identical for everyone.

Nucleus's bet: a whole human life is roughly 876K hours of perception, and frontier models already pre-train on millions of hours — so a single life fits. Give each user their own adapter on an open vision-language model and fine-tune it nightly on what they actually lived. The model that answers you tomorrow remembers yesterday, because it was trained on it overnight.

For that to work, something has to turn raw capture into clean, timestamped language. That is our whole job.

Two loops, one system

LEARN LOOP · background, nightly — this is our loop
User's life→ Recording
capture · chunking→ C1 → DATA-PROCESSING
ASR · diarize · caption · OCR→ C2 → Storage /context→ C10 → Continuum
nightly fine-tune
SERVE LOOP · interactive, seconds — not ours, but know it exists
User asks→ Input / QueryBuilder→ Inference
the user's own adapter→ Output→ User

We sit in the middle of the learn loop, with two neighbours and one contract each.

  • C1 comes in from recording. A small envelope per chunk: who and which device, the wall-clock span, the modality and codec, and a reference to raw bytes recording already put in storage. We pull the bytes by that reference.
  • C2 goes out to storage. One processed record per chunk, written to the context store. Modules 03 to 05 are about almost nothing else.
  • C8 is promised and unbuilt. The same pipeline offered synchronously, so an interactive request gets normalised by identical code. No such surface exists — but the inline path in module 09 is kept deliberately as its skeleton.
The boundary that defines us

We interpret, and nobody upstream of us may. Recording is forbidden from transcribing or captioning, precisely so there is exactly one place where bytes become claims about a person's life. The flip side is the burden: our output is the training set, so the quality ceiling of the whole product is set here.

MODULE 02 Vocabulary

Speak data-processing before you read data-processing

Twelve words carry this whole service, and three of them look interchangeable until they bite you. Click each card.

chunkthe unit of everything

A few seconds of one captured stream, and the thing everything is keyed on. Recording carves streams into chunks; each carries an id, and that id is how we recognise it if it arrives again.

A chunk is strictly one modality — audio or video, never both. Recording splits mixed capture before we ever see it.

recordour only output

The one object we write per chunk, to storage's context store. It carries provenance back to the chunk, the wall-clock span, the dialect string, and a map of slots.

Exactly one per chunk. Not a guideline — the machinery can only produce one, and a test asserts it.

slotone named finding

One named entry in a record's slots map. Six exist today: asr, diarization, transcript, acoustic, caption, ocr.

Each is written by exactly one stage, exactly once, and never edited afterwards. That single rule is what makes "who wrote this?" answerable from the record alone, forever.

stageone processing step

One step, declared in one file. It states which other stages it needs, which single slot it produces, whether it is required, how many bytes its slot may occupy, and who consumes it.

Adding a step means adding a file. There is no registry to edit and no wiring to update.

backendthe implementation

The concrete thing behind a stage: a model and how it is called. fw is faster-whisper, pyannote is the diarizer, ppocr is the text recogniser.

Chosen in code, never by configuration, and named in the version string so you can always see which one ran.

executorthe machinery

The part that runs one chunk's stages: it works out which may start, runs them, collects each slot, and assembles the single record.

When this guide says something holds "by construction", the executor is usually what constructs it.

pipeline_versionalso called the dialect

A plain string naming every enabled stage and the versions it ran at, joined with plus signs in sorted order.

It states what was attempted, never what succeeded — and it is half of a record's identity, which makes it the most load-bearing string in the service.

segmentthree unrelated meanings

Here it means one stage's piece of the dialect string, shaped <stage>.v<S>-<backend>.v<B>. Each slot carries a copy of its producer's segment.

Watch out: recording calls its ten-second upload unit a segment, and storage's day-log calls its time slices segments. Three things, one word. Neither of the other two ever reaches us.

holeattempted and failed

A slot that was tried and failed, and is therefore simply absent from the record.

Sharply different from a slot that is present and empty, which is a positive claim that we looked and found nothing. Collapsing those two is the mistake this service exists to prevent.

heala second chance

Re-running a chunk's whole graph on a later delivery to fill its holes, writing to the same record address because the dialect has not changed.

Bounded by a budget of three — and a heal that comes back completely clean is never charged against it.

model servermachinery, not us

A long-lived process holding one model in memory, answering HTTP requests, and reporting exactly what it is at /health.

Four of them run under our own supervisor, two replicas each. No model is ever loaded inside this service.

day-logdownstream artifact

The rendered account of a span of someone's life that storage builds from our records, and the thing the trainer actually reads.

Ours to feed, storage's to render. Our slot names decide which lines appear in it.

The three that bite

Stage, slot, segment. A stage is a step; a slot is what it writes; a segment is its piece of the version string. They travel together and are deliberately named differently. When a stage declares what it needs it names stages — naming a slot there is the most common first mistake, and it fails immediately.

Why a map of slots, rather than a fixed set of fields

  • New capabilities don't reshape anything. Adding acoustic tagging adds a key; nothing existing changes shape and no other consumer has to care.
  • Nobody can overwrite anybody. One key, one writer, forever. Two steps working near each other cannot quietly clobber each other.
  • Provenance is free. Each slot carries a copy of its producer's version segment, so "what made this?" is answerable from the slot alone.
  • Derived views are new slots, never edits. Want a transcript with speakers attached? Don't edit the speech slot or the diarization slot — add a stage that reads both and writes a third slot. That is exactly what transcript is above.
Look at the acoustic slot

Its value is an empty list. That is not missing data and not a bug: it is the acoustic tagger saying, on the record, that it ran and heard nothing worth naming. A slot present and empty is a claim. A slot that is absent is something else entirely, and module 06 gives that distinction its full weight.

MODULE 04 Identity

Why the same chunk can arrive twice and nothing bad happens

Two components, one hash, and the trick that makes an at-least-once wire behave exactly-once.

A record's address is the SHA-256 of exactly two things, joined by a zero byte:

record_id = sha256( chunk_id + NUL + pipeline_version )

Both inputs are printed inside the record, so anyone holding one can recompute its address and check it. Here is that computation on the very record from module 03:

chunk_id 01KZDHFJGFA0CWYJQY4BST5JHA
separator one NUL byte (0x00)
pipeline_version acoustic.v1-ast.v1+asr.v1-fw.v1+diarize.v1-pyannote.v1+speaker_align.v1-builtin.v1
sha256 d613aabfd56d93522f2432ab842d1c61452beb6da50bc843ad32c9ca284cd382

Verified 2026-08-08 against both the record storage served and the journal row for that chunk.

Three facts, and what they add up to

  • Writing to storage is a blind upsert. Storage does not ask whether it has seen the record before. It writes it at that address, full stop.
  • The same chunk under the same dialect gives byte-identical output. Nothing time-varying is allowed inside a record — there is deliberately no "processed at" field, because a wall-clock value would make every reprocess differ.
  • So a redelivery computes the same address and writes the same bytes there. The wire is at-least-once; the effect is exactly-once.

That is why redelivery is boring rather than frightening. Nobody coordinates, no lock is held across services, and a chunk re-pushed after a retry, a restart, or an operator's replay is simply harmless.

Why a zero byte in the middle?

Without a separator that cannot occur in either component, two different pairs could concatenate into the same string and collide. Chunk ids and dialect strings are both text; a NUL byte is not text, so nothing can smuggle one across the boundary.

The corollary you will use constantly

Change the dialect and you change the address. A record processed under a new version does not overwrite the old one — it lands beside it, at a different id, and both exist in storage, each honestly labelled with the processing that produced it. That is "version-forward", and it is why bumping a version is a safe act.

MODULE 05 The version law

The dialect: what was attempted, stated before anything runs

Every stage declares two version numbers. Bump one in the composer and watch a record's identity move.

Stage version — the contract

What the stage promises: what it needs, what its slot is called and what shape it has, what emitting it means, its byte budget.

Backend version — the implementation

How it keeps that promise: the model, the weights, the prompts, the thresholds, any behaviour at all.

Together with their names those form the stage's segment, and the dialect is every enabled stage's segment, sorted and joined with plus signs.

compose a dialect click a stage to bump its backend →
dialect (sorted, +-joined)
record_id this chunk would get

No environment variable may change what a record says

This surprises people who have worked on services where a knob tunes the output. Here, behaviour lives in code or it does not exist.

  • A stage is never handed the settings. Its context carries the envelope, the raw bytes, its inputs and its clients — no configuration at all.
  • Twenty environment variables exist, and every one is operational. Where storage lives, which endpoint to call, how many workers, how long to wait, whether metrics are on.
  • This is enforced, not encouraged. One test runs fixed bytes across a matrix of environments and demands byte-identical records. Another reads every environment variable the code touches and fails when a new name appears that was not declared operational.
  • Experiments must be visible. An in-code A/B has to surface as an .exp- suffix, or it is forbidden — otherwise two records would claim to be the same thing while holding different answers.

A live example: the code and the fleet disagree right now

The dialect is resolved from the stage declarations the running process loaded when it started. Python reads a module once; editing the file afterwards changes nothing until something restarts.

MODULE 06 Stages & honesty

How work is scheduled, and the three answers a record can give

Required versus optional, what a hole really is, and the distinction the whole design exists to protect.

The stages that run today

  • Needs names stages, not slots. speaker_align needs diarize, even though the slot it reads is called diarization. Naming the slot fails immediately with "needs unknown stage".
  • A stage need not produce a slot. clipprep decodes video into frames that live only for the run and are freed once the last consumer finishes, so no bytes reach the record. Its budget of 1 is real but can never fire — every stage must declare a positive budget, and this one has nothing to measure.
  • The byte budget is a hard ceiling. Going over is a stage failure, never a silent truncation, because a quietly shortened transcript is a lie nothing downstream can detect.
  • Six audio files, four stages. Speech translation and an injected-caption stage for replay work are written, tested, and deliberately left unregistered — absent from the dialect, never run. Expect that when you open the directory.

Nothing waits for a phase — a stage starts when its needs are done

There is no ordering attribute and no topological loop. Every stage becomes one task inside a single task group, and each awaits exactly the stages it declared. A stage with no dependencies starts immediately; a stage with dependencies starts the instant they finish. The graph runs itself.

Required and optional differ by construction

A required stage fails → no record at all

Every sibling is cancelled and awaited, the original error is re-raised, and the attempt fails. Nothing partial is written. The chunk goes to the worker's retry path, then a durable dead letter.

An optional stage fails → a hole, and the record ships

Its slot is never written, everything downstream of it is marked cancelled without running, and the record goes out carrying whatever else succeeded.

Because those behaviours differ so much, the resolver refuses to build a graph where a required stage sits downstream of an optional one — that would make the optional stage required in fact while claiming otherwise.

The three answers, and why they must stay apart

This is the idea the entire service is arranged around. Given a record and its dialect, a consumer can tell three completely different situations apart.

✓ We looked, nothing there

Stage in the dialect, slot present, value empty.

"acoustic": {"values": []} — the tagger ran and heard nothing. A positive claim.

✗ We tried and failed

Stage in the dialect, slot absent. A hole.

A server was down, a budget was blown. We say so rather than pretend.

— We never tried

Stage not in the dialect at all.

This chunk ran a pipeline without that step. The record is silent, and no conclusion may be drawn.

The rule that falls out of it

A consumer may never infer a negative from an absent slot under a dialect that did not attempt it. If the on-screen-text stage is not in the dialect, the correct reading is not "there was no text on the screen" — it is "nobody looked". Get this wrong downstream and the trainer learns that someone's screen was blank during hours it was never examined.

MODULE 08 Machinery & bureaucracy

Where the models actually live

Four supervised models in eight processes, a fifth over the network, and one shutdown fact you must get right.

The split at the centre of the design: models are machinery — heavy, slow to load, worth keeping warm. This service is bureaucracy — a thin orchestrator that decides, calls, and writes down. No model is ever loaded inside this process; a stage is a client.

That check exists to stop the most frightening failure in a system like this: a replica quietly restarting onto different weights and producing subtly different transcripts under an unchanged dialect string, forever, with nothing in the data to reveal it.

When a server dies mid-chunk

  • The client handles the call. Three attempts by default, dealt round-robin across that server's replicas — which is the entire reason two of each exist. One replica dying is usually invisible: attempt two lands on its twin. With two replicas, attempt three comes back round to the first.
  • The supervisor handles the process. It polls health every five seconds and, after three consecutive failures, restarts the replica on a backoff ladder of one, two, five, ten and thirty seconds, resetting once it has been healthy for a minute.
  • Then the stage's policy decides everything. Diarization is optional, so its slot becomes a hole and the record still ships with a transcript. Speech recognition is required, so the chunk attempt fails and goes to the retry path.

The supervisor lives inside this process

It is not a separate program — it is a task on this service's own event loop, which makes this service the direct parent of all eight replicas. Checked on the running node on 2026-08-08: the service was process 632026, and all eight model servers reported it as their parent. The numbers change on every restart; the parentage does not.

A graceful stop takes the fleet with it

The service drains its queue, then walks the replicas and signals each to terminate, waiting up to ten seconds before forcing it. Because they are reaped one at a time, a worst-case orderly shutdown takes the drain timeout plus ten seconds per replica.

A hard kill leaves all eight running

The shutdown code never executes, so nothing ever signals the replicas. All eight survive as orphans holding their ports; six also hold GPU memory, the two OCR replicas being CPU-only. A restarted service cannot bind those ports until they are reaped by hand.

Get the reason right — the obvious one is wrong

It is tempting to say the replicas survive because they are started in their own sessions, and you will meet that explanation compressed into a clause in the charter's own summary. The observation is true; the causation is not. On Linux nothing kills a child when its parent dies — an orphan is simply re-parented and keeps running, session or no session.

The real reason is narrower and more useful: an unblockable kill cannot be handled, so the shutdown path never runs, so nothing ever signals the replicas. The separate sessions exist for a different job entirely — they let the supervisor signal a replica's whole process tree without signalling itself.

MODULE 09 Hard-won correctness

Crashes, redelivery, and healing

What survives a kill, how a redelivery is judged, and why a successful repair is never charged.

Two ingest modes, both real

  • Inline runs the whole pipeline inside the request and returns the finished record's id. It is kept deliberately as the skeleton of the synchronous contract module 01 mentioned.
  • Async writes the chunk down durably, answers 202, and processes it on a worker. This is what the deployment runs.
  • For one chunk the two produce identical bytes. What differs is only what the acknowledgement promises.

Before either, the request passes gates in a fixed order: a malformed body is a 400, an envelope failing the contract is a 422, and a modality with no pipeline is a 501. These are answered synchronously in both modes, because a request that can never succeed should be told so immediately.

What the 202 actually promises

Inline, a success reply means the record is durable in storage. Async, the 202 is returned as soon as the chunk is safely journalled — before any stage has run. It promises only that we have durably taken responsibility. What tells recording a chunk is genuinely done is not the acknowledgement at all: it is the chunk appearing as processed on /continuity, which happens only after storage confirms.

The claim tree: five verdicts on every delivery

Once a delivery is real work, the service asks the journal what it already knows about this chunk. That question has exactly five answers. The buttons offer six situations, because two different roads reach the same verdict of skip.

Healing, and the budget that bounds it

  • A heal is a full re-run writing to the same address, because the dialect has not changed. The redelivery carries the original envelope, so nothing had to be stored to make it possible.
  • A heal that still has holes costs one attempt from a budget of three. At the budget the holes go permanent, the row is marked final, and future deliveries under that dialect skip forever.
  • A heal that comes back completely clean is never charged. The budget exists to stop a chunk whose holes are structural from being re-run against the fleet forever; a repair that actually worked is not evidence of that.
A heal does not always make a record fuller

It is tempting to read healing as monotone improvement. It is not: a heal re-posts whatever the re-run produced, so a heal that happens during a different server's outage can leave a previously-filled slot missing. The guarantee is that repeated healing converges, not that every step improves. Hole truth lives in the journal's per-stage statuses, which is why the journal, not the record, is what you read to learn what failed.

What survives a crash

Killed at this momentWhat survivesWhat happens next
Before the accepted row is writtenNothing on our sideRecording never got an acknowledgement, so it re-pushes. Processed as fresh.
After the row, before the 202The accepted rowStartup re-drives it. Recording may re-push too; both converge, because the address is deterministic.

After the receipt is writtenEverythingA later delivery reads the receipt: green means skip; holes with budget left means heal.

Three protections that keep that table honest

  • Failures are classified before retrying. A transient failure, like a model server timing out, is retried a few times with a lengthening pause, and a chunk waiting out that pause releases its worker slot so it cannot block the queue. A terminal failure, like an envelope that produced an invalid record, is never retried, because the same code cannot succeed on the same input.
  • Every acceptance bumps an epoch, and terminal writes are guarded on it — so a worker finishing late cannot clobber a fresher attempt that has already re-accepted the chunk.
  • Startup re-drives are counted. Past the cap, a chunk that crashes the service every time takes one of two exits: with no record yet it is dead-lettered; with a durable record already written it is marked finished with its holes permanent, because dead-lettering a chunk whose record exists would report a loss that never happened.

A dead letter is durable and reported on /continuity, which is how recording learns a chunk is genuinely lost rather than merely slow. That is what keeps a lost chunk reading as a gap on its side and never as clean.

MODULE 10 Downstream

Storage's side, and the line the trainer reads

Where the record lands, what makes it move between training windows, and how slots become sentences.

We make exactly one write per completed attempt: a single atomic post of the whole record. Partial writes are forbidden — there is no state in which half a record exists.

Two timestamps we never set

  • created_at is the first time that address was ever written.
  • updated_at moves only when the posted record differs byte for byte from what is stored.

That comparison is the quiet hero of the redelivery story. A duplicate re-posts identical bytes, the comparison finds no difference, and the record is not touched: it does not move to a new training window and does not get re-learned. A heal that genuinely changed something does differ, so it does move — a cost the design accepts deliberately.

Slots become lines

SlotDay-log line
captionScene:
ocrWorld text (OCR):
transcriptHeard: — speaker-bucketed, one line per turn
asrHeard: — the fallback when transcript is absent, speakers unlabelled

A hole renders as absence: the line simply is not there. An empty value renders as nothing to say. Neither invents a sentence claiming the opposite — and neither is distinguishable from the other in the rendered text, which is exactly why the record and its dialect, not the day-log, are where you go to ask what happened.

The whole service, traced backwards

Those words were spoken into a microphone. Recording carved them into a chunk and stored the bytes. We pulled the bytes, sent them to a speech model on port 8121 and the same bytes to a diarizer on 8131, combined the two answers into a third slot, and wrote one record at an address derived from the chunk id and the dialect.

Storage compared it byte for byte with what it had, kept it, and rendered its transcript slot into that line. Tonight the trainer reads the line.

What our choices oblige the neighbours to do

  • Recording must not treat our acknowledgement as completion. Because async answers 202 before any work happens, recording confirms a chunk only when our continuity endpoint reports it processed. That is what keeps a lost chunk from ever reading as clean.
  • Storage must compare bytes, not just addresses. Our determinism is only useful if a no-op redelivery leaves the stored record untouched, so storage bumps its changed-at timestamp only on a genuine byte difference.
  • Continuum must never infer a negative from a missing line. A day-log without an on-screen-text line may mean the screen was blank, or that the stage failed, or that it never ran. Only the record and its dialect can tell.
  • Adding a slot is a contract edit. Unknown slot names fail closed at storage, deliberately — the edit is the ceremony that makes a new kind of claim about someone's life a visible act.

MODULE 13 Codebase & day one

The map, and how to run the thing

Where everything lives, the commands you'll type, and the two traps that cost an afternoon.

The map

PathWhat lives there
app/main.pyThe HTTP routes, the ingest gates, the claim decision, the worker pool wiring

app/stages/<modality>/One file per processing step. This is where you add work

Adding a stage

  1. Drop one file under the stage directory for your modality, subclass the stage base, and decorate it so it registers itself.
  2. Declare the surface: what you need, your slot, required or optional, a byte budget you can defend, and who consumes the slot.
  3. Write exactly one run method — a synchronous one if it does real work, since that runs in a worker thread, or an asynchronous one if it only makes network calls.
  4. If the slot is new to the record, add its name and shape to the C2 contract. Unknown slot names fail closed, and that edit is the ceremony.
  5. Run the suite. If your change alters what any existing record would contain, you owe a version bump.

Running the suite

cd product/services/data-processing
./.venv/bin/python -m pytest -q

On 2026-08-08 that took 55 seconds and reported 569 passed, 4 skipped. The skips are drills needing real hardware; they spawn the fleet on GPUs and run only when asked.

Trap one — never run a hand-picked subset of the law tests

Running the determinism file and the composition file together produces two failures that do not exist in the full suite. The determinism tests import the stage modules under a deliberately emptied registry; Python caches modules, so their registration can never fire again in that process, and the composition test then sees an empty registry. The full suite stays green because other files import those modules earlier and normally. Run everything, or don't trust the result.

Trap two — nothing runs these for you

The charter describes the law as enforced in continuous integration. Today the only automated workflow checks markdown style; no runner executes this suite. The discipline is yours, before you push.

Goldens and drills

  • Each model server keeps a golden — a recorded output of the real model on real bytes, with a written record of how its determinism was established.
  • Stage tests replay that golden through a fake client and pin the resulting slot. A red therefore tells you which thing broke, because the model stack and your mapping of its output live in different files.
  • There is no regeneration script, deliberately. Re-blessing a golden is a decision, and it rewrites the provenance note in the same commit.
