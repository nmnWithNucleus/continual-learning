The Data Processing Service is where a captured life becomes language.

Raw audio and video chunks flow in from recording; one structured, timestamped record per chunk flows out to storage. Every token the per-user model is ever trained on passes through this pipeline, so the quality ceiling of the whole product is set here. This guide teaches the service as it runs today — the rebuilt v1 world that replaced the old multi-record, in-place-mutation model at the Stage F cutover.

Module 00 · Briefing

What you're joining, in ninety seconds

The shortest true description of the service, before any detail.

Data processing takes a few seconds of someone's captured life — a slice of audio, a slice of screen or camera video — and writes down what it contained: the words spoken, the scene described, the text on the screen, each stamped with the wall-clock time it happened. Recording hands us those slices over HTTP; we pull the raw bytes from storage, run them through a small graph of processing steps, and write one record back to storage's /context store. Tonight, the continuum service reads those records and trains the user's personal model on them.

The service was rebuilt from the ground up in 2026 (Stages A–G, ratified as decisions D23–D28). The rebuild replaced a complicated model — one slice could become several records, and a later step could edit an earlier step's record in place — with a strict, simpler one whose good behaviour holds by construction: one slice becomes exactly one record, each field written by exactly one step and never edited. If you learned the old world from an earlier version of this guide, module 03 is where the difference lives.

The old world needed a book of governance (a five-test emission law, discriminators, capability views) to keep multi-record mutation honest. The rebuild deleted the capabilities, so the governance had nothing left to govern. The tombstone for those retired concepts is the charter's §Condensed history — read it once you know the new world, not before.

Module 01 · Orientation

Why Nucleus exists, and where DP sits

The product promise, and our one job inside it.

Nucleus is building a personal model that genuinely knows you — trained, night after night, on your own captured life. For that to work, someone has to turn the raw capture into clean, timestamped, structured text the model can learn from. That is us. We sit between two neighbours and speak to each through one contract apiece:

recording— C1 → data-processing :8085— C2 → storage /context→ continuum (nightly training)
  • C1 in — recording pushes a small envelope per chunk: who and which device, the wall-clock span, the modality and codec, and a blob_ref pointing at the raw bytes it already stored in storage's /raw. We pull the bytes by that ref.
  • C2 out — we write one processed record per chunk to storage's /context. That record, and how it is built, is the heart of this guide (module 03).
  • C8 — designed, not built. The same pipeline is meant to be offered synchronously to the input service, so an interactive request (you paste a screenshot into chat) is normalised by the exact same code as the life stream. Nothing is built yet; the inline ingest path is kept alive deliberately as C8's skeleton, which is why you will see it beside the async path in module 08.

We own no capture devices, no storage engine, and no training. Recording owns the first; storage owns /raw, /context and the day-log; continuum owns the nightly fine-tune. Our contract with quality is simple and total: if we write it wrong, the model learns it wrong.

Module 02 · Vocabulary

Speak DP before you read DP

Ten words. The rest of the guide assumes them. None is optional.

chunk

A few seconds of one captured stream — the unit everything is keyed on. Recording carves the stream into chunks; we dedup on the chunk's id.

record

The one C2 object we write per chunk. It carries provenance, the time span, the dialect string, and a content.slots map. Exactly one per chunk (Slot Law L2).

slot

One named field inside a record's content.slots — asr, transcript, caption, ocr, acoustic. Each is written by exactly one step and never edited.

stage

One processing step in the graph — e.g. asr, diarize, clipcap. It declares what it needs, which one slot it produces, and whether it is required.

backend

The concrete implementation a stage runs — a model and its settings (fw for faster-whisper, vlm for the captioner, mock in tests). Named in the dialect.

pipeline_version the dialect

A plain string naming every enabled stage and its versions, e.g. asr.v1-fw.v1+diarize.v1-pyannote.v1+…. It states which processing produced a record. The trainer must see one dialect per chunk.

hole

A slot that was attempted and failed — so it is simply absent from the record. Distinct from a slot present with an empty value (an honest "nothing there").

heal

Re-running a chunk's whole graph on redelivery to fill a hole, re-writing the same record. Convergence, not monotonicity, is the promise (module 07).

machinery / bureaucracy

The split at the centre of the design: models are long-lived machinery (server processes); the DP service is thin bureaucracy (an async orchestrator that calls them). No model loads inside DP.

model server

One replicated, GPU-pinned process per model (servers/whisper, pyannote, ast, ocr), health-checked and restarted by a supervisor that lives in DP.

Two more you will meet from the neighbours: the day-log is the account of a day that storage renders from our records for the trainer, and a window is the span one night's training covers. Both are storage's, not ours — but our records are what they are built from.

Module 03 · The core

One record per chunk, built from slots

If you remember one thing from this guide, remember this shape.

A C2 v1 record is one object per chunk. Its identity is a hash of exactly two things — the chunk id and the dialect — and writing it to storage is a blind upsert on that id. Its content is a map of slots: each key is a slot name, each value was written by one stage, and no stage ever edits another stage's slot.

{
  "contract": "C2", "version": "1",
  "record_id": "sha256(chunk_id ␀ pipeline_version)",
  "user_id": "nmn",
  "modality": "audio",
  "source": { "device_id": "...", "stream_id": "...", "chunk_id": "...",
              "blob_ref": "raw/...", "device_tz": "Asia/Tokyo" },
  "t_start": "2026-07-19T17:04:10Z",
  "t_end":   "2026-07-19T17:04:22Z",
  "pipeline_version": "asr.v1-fw.v1+diarize.v1-pyannote.v1+speaker_align.v1-builtin.v1+acoustic.v1-ast.v1",
  "content": {
    "slots": {
      "asr":         { "version": "asr.v1-fw.v1", "language": "en", "value": "...", "splits": [ ... ] },
      "diarization": { "version": "diarize.v1-pyannote.v1", "splits": [ ... ] },
      "transcript":  { "version": "speaker_align.v1-builtin.v1", "splits": [ ... ] },
      "acoustic":    { "version": "acoustic.v1-ast.v1", "values": ["keyboard typing"], "confidence": 0.87 }
    }
  }
}
Slot Law L2 · L3 · L5

One record per (chunk_id, pipeline_version), the executor structurally emits one and a test asserts it (L2). Identity is two components, NUL-joined and hashed — there is no third "discriminator" component, because with one record per chunk there are no siblings to tell apart (L3). Content is a slot map, one producer per slot, each written once and never edited (L5). A speaker-aligned transcript is not an edit of the raw ASR — it is a new slot from an ordinary stage whose inputs are the ASR and diarization slots.

A video chunk has the same shape: one record with a caption slot and an ocr slot. In the old world that was two records told apart by a discriminator; now it is two slots in one record. Storage assigns the durable timestamps (created_at, updated_at) — there is deliberately no wall-clock inside the record, so a re-run under the same dialect is byte-identical.

Module 04 · Identity

The version law — identity lives in code, never in config

Why there is no knob that changes what a record says.

The dialect string is the +-joined, sorted list of every enabled stage's segment <stage>.v<S>-<backend>.v<B>, resolved before any stage runs. It states the attempted dialect, and it is the second half of every record's identity. Two rules keep it honest:

  • Stage version vS bumps on a contract change — the stage's needs, its slot's name or shape, its emit semantics, its byte budget. Backend version vB bumps on an implementation change — the model, its weights, its prompts, its thresholds, any behaviour.
  • No output-affecting env knob exists. Every environment variable is operational only — endpoints, replica counts, timeouts, log levels. A determinism test in CI proves it: fixed bytes and fixed versions produce a byte-identical record across the whole settings matrix. If a knob could move one byte of a record, the test goes red.

A worked example from Stage GWhen the legacy prompt pack was deleted, the aggregate prompt-pack digest changed. Because a registration guard welds that digest to the captioner's backend version, the change forced a vB bump — the captioner's pin went clipcap.v1-vlm.v1 → clipcap.v1-vlm.v2. The bump is code-true today and wire-true only after the next deliberate fleet restart deploys it: the running process imported the old pack, so live video records still stamp vlm.v1 until then (module 09). Nobody could quietly change a model-facing prompt without the dialect forking; that is the law working.

Experiments fork the dialect too. An in-code A/B must surface its treatment in the string as .exp-<code> — invisible-to-identity experimentation is forbidden, so an experimental caption can never be mistaken for a real one in the training corpus.

Module 05 · Architecture

Machinery and bureaucracy — the split at the centre

Where the models live, and why not inside DP.

Every model — ASR, diarization, acoustic tagging, OCR, the video captioner — runs as a long-lived server process: loaded once, kept warm, GPU-pinned, health-checked, and restarted on crash. Those are the machinery. The DP service itself is bureaucracy: a thin async orchestrator that, per chunk, prepares a request, calls a model server over HTTP, and folds the reply into a slot. No model loads inside the DP process, and there are no per-chunk child processes.

The supervisor lives inside DP for now. It reads a manifest — which servers, how many replicas, which GPU each pins to — and spawns, health-checks and restarts them. A stage talks to a server through a thin client that picks a replica, enforces a per-call timeout, and retries a transient failure on another replica. When a replica dies, the supervisor brings it back; when all replicas fail one input the same way, that is a real failure and the next module owns what happens.

This split is why the old INGEST_ISOLATION subprocess shield is gone: it existed to contain a model crash inside the DP process. With the models outside, a poison chunk fails one stage client and the supervisor restarts a dead replica — there is nothing left in DP to isolate.

Module 06 · The two modalities

Slots in practice — audio and video

Which stages produce which slots, and how a chunk becomes a record.

Audio

An audio chunk runs a VAD-gated ASR plus diarization and acoustic tagging. Four stages, four slots — and a fifth stage, speaker_align, that reads two of them to produce a derived one:

Video (screen)

A screen-video chunk becomes one record with two slots. Frame prep is a self-isolating ffmpeg subprocess; the OCR server reads the on-screen text; the captioner writes the scene, with the OCR text injected into its prompt for grounding.

Module 07 · Failure

Failure and healing — required, optional, holes

What happens when a stage cannot do its job.

Every stage declares whether it is required. The two failure paths are different by construction:

  • A required stage fails ⇒ no record. The chunk attempt fails, the worker retries it, and if it keeps failing it is durably dead-lettered — which storage's neighbour, recording, sees as gaps, never as a falsely-clean day.
  • An optional stage fails ⇒ a hole. Its slot is simply absent, the steps that depended on it are cancelled, and the record ships with the slots that succeeded. A reader can tell a hole (stage in the dialect, slot absent) from an honest empty value (stage ran, found nothing) from a stage that never ran (not in the dialect at all). That is Slot Law L11.

Healing

The journal keeps a done-row per chunk: its dialect, its record id, each stage's status, and how many heals it has spent. When a chunk is redelivered, the row decides what happens — no row means process fresh; a different dialect means reprocess and land a new record beside the old; the same dialect all-green means skip (return the record id); the same dialect with holes and budget left means heal. A heal re-runs the whole graph and re-writes the same record id, so a hole that the fleet can now fill converges. The promise is convergence, not monotonicity: the re-run writes whatever it produced, and the ledger — not the record — carries the truth about which holes remain.

This was proven live at the Stage F cutover: an optional stage was killed so a chunk shipped with a hole, the supervisor restarted the model, and the chunk's redelivery healed the record to be byte-identical to a clean-fleet twin — then a further redelivery was a pure skip.

Module 08 · Reliability

Crash safety — async ingest and the durable journal

How the service refuses to lose a chunk silently.

Ingest is async today: recording pushes a chunk, DP writes it durably to a journal and answers 202 Accepted immediately, and a bounded pool of workers drains the queue. Capture never blocks on model latency, and a full queue answers 503 so overload is visible backpressure rather than a silent drop. A redelivery of a finished chunk returns its record id with a 200; an in-flight one re-acknowledges 202.

The safety net is a shared, honest accounting between us and recording. DP's /continuity reports, per stream, which chunks are processed and which were dead-lettered; recording marks a chunk truly confirmed only when DP says processed. So an accepted-then-lost chunk reads as recording or gaps in recording's report — never a false clean.

Proven at the Stage F soakThe service was hard-killed (SIGKILL) with 27 chunks durably accepted-but-unprocessed in its journal. On restart the boot re-drive re-enqueued all 27 and every one reached processed — zero in-flight loss across a crash. The durable journal is what makes that true.

The inline path is kept alive on purpose. It is byte-identical to async for a single chunk and it is C8's skeleton — the synchronous shape the input service will call one day. Do not delete it "because async exists"; that has been proposed and refused on exactly this ground.

Module 09 · Honesty

What is real, and what is not

A teaching view that hides the gaps misleads the reader who cannot yet see them. So here they are.

realAudio & video, end to end

Real faster-whisper, pyannote, AST and PP-OCR servers, and a real Qwen3-VL captioner, all ran a synthetic multi-hour soak through the live fleet at the cutover. Records are C2 v1, one per chunk.

realCrash safety

The durable journal, async ingest, heal-on-redrive and the zero-silent-loss accounting are built and drilled, including a live in-flight-kill recovery.

partialBackfill by version

Reprocessing a whole day under a new dialect from the kept /raw bytes is designed (the OD-2 tool) but not built. Kill/restart recovery is done; the replay tool is owed.

designedC8 — the synchronous API

Offering the pipeline to the input service for interactive requests. Nothing is built; the inline path is its skeleton.

designedWorld-data enrichment

Known-faces, geolocation, place/object tags (charter M5). Not built; slots make it an additive change when it lands.

watchVideo throughput

CPU OCR plus a 32B captioner per video chunk is the slow leg; there is no per-modality fairness cap yet, so a video burst can starve audio. Named at the soak, tuned later.

pendingThe vlm.v2 dialect flip

Stage G's prompt-pack demolition re-pinned the digest and bumped the captioner to clipcap.v1-vlm.v2 — in code. The running fleet predates the bump and still stamps vlm.v1; the flip deploys at the next deliberate restart (module 04's worked example).

The retired v0 world — the emission law, discriminators, capability views, the env-flippable dialect freeze, the two-record video shape — is not taught here because it no longer runs. If you need to know why those existed and what killed them, the charter's §Condensed history is the six-paragraph tombstone.
